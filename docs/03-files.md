# Диаграмма файлов приложения

Структура повторяет архитектуру из ЛР № 3 (C4, уровень 2): клиенты → API →
сервисы → PostgreSQL, плюс отдельный процесс-воркер уведомлений. В этой работе
появились каталоги `api/`, `mcp/` и `db/` — они и есть новая часть приложения.

## 2. Соответствие «каталог — слой архитектуры»

| Каталог | Слой (C4 L2) | Что здесь лежит |
|---|---|---|
| `api/` | Внешний контракт | Спецификация и примеры; кодом не является, но определяет контракт для бэкенда и клиентов |
| `db/` | Хранилище | DDL и данные; источник истины для схемы |
| `mcp/` | Интеграция с ассистентом | Отдельный процесс, обращается к своей mock-базе, не к рабочей |
| `docs/` | Документация | Страницы вики, они же содержимое GitHub Pages |
| `tools/` | Сборка артефактов | Генератор, в поставку приложения не входит |

## 3. Поток данных в MCP-сервере

```
LLM-клиент (Claude Desktop / Cursor / Inspector)
        │  MCP (stdio, JSON-RPC)
        ▼
mcp/server.py ── Tools ─────► SQLite (mcp/campus.db)
        │        Resources ─► только чтение
        └──────── Prompts ──► текст-инструкция для модели
```

Почему у MCP-сервера своя база, а не рабочая PostgreSQL: демонстрация не должна
оставлять следов в данных, а mock-база поднимается одной командой на любой машине
без Docker. Схема SQLite повторяет физическую модель по смыслу (четыре таблицы
из четырнадцати — те, что нужны трём инструментам).

## 4. Что появится дальше

Веб-приложение (`web/`) и мобильное приложение (`mobile/`) выносятся в отдельные
репозитории, как требует задание 6. В основном репозитории останутся только
контракт (`api/`), модель данных (`db/`) и документация (`docs/`).
