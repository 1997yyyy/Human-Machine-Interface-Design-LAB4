# MCP-сервер Campus Events

MVP MCP-сервера из задания 5: три действия, два источника данных и один шаблон
промпта. Ассистент может записать студента на сессию, отменить запись и отметить
билет — те же операции, что делает API, но с проверками бизнес-правил и
структурированными ошибками.

## 1. Что умеет

### Инструменты (Tools)

| Инструмент | Параметры | Что делает | Коды ошибок |
|---|---|---|---|
| `create_registration` | `session_id`, `user_id` | Проверяет публикацию, дубликат и места; создаёт запись и билет; увеличивает счётчик | `NOT_FOUND`, `SESSION_CLOSED`, `ALREADY_REGISTERED`, `NO_SEATS` |
| `cancel_registration` | `registration_id`, `reason` | Отменяет запись, отзывает билет, освобождает место и выдаёт предложение первому в очереди | `NOT_FOUND`, `ALREADY_CANCELLED`, `TICKET_USED` |
| `check_in_ticket` | `qr_payload` | Отмечает присутствие; повторный вызов идемпотентен | `NOT_FOUND`, `TICKET_REVOKED` |

Схемы параметров строятся из аннотаций типов: строки и `str` с описанием в
docstring, поэтому MCP-клиент видит у инструмента типизированную JSON-схему —
это требование задания («принципы типизации из документации MCP Python SDK»).

### Ресурсы (Resources)

| URI | Содержимое |
|---|---|
| `catalog://events` | Опубликованные мероприятия с сессиями и числом свободных мест |
| `registrations://user/{user_id}` | Записи пользователя: статус, время, статус билета |

Персональные данные не отдаются: в ресурсе нет `email` и телефона, только ФИО,
группа и статусы.

### Шаблон промпта (Prompts)

`registration_help(event_title)` — задаёт модели порядок работы: прочитать каталог,
проверить места, только потом вызвать инструмент; при `NO_SEATS` не повторять
вызов, а предложить лист ожидания.

## 2. Развёртывание

```bash
# 1. Зависимости
pip install -r ../requirements.txt      # mcp, PyYAML, openapi-spec-validator

# 2. Mock-база (6 пользователей, 3 мероприятия, 4 сессии)
python make_mock_db.py                  # создаст campus.db рядом со скриптом

# 3. Проверка без LLM: 10 сценариев, печатает результат каждого
python test_mcp.py

# 4. Подключение к ассистенту (stdio)
python server.py
```

Переменная окружения `CAMPUS_DB` переопределяет путь к базе; по умолчанию
`mcp/campus.db`.

### MCP Inspector (без ассистента)

```bash
npx @modelcontextprotocol/inspector python mcp/server.py
```

В браузере открывается панель: вкладка *Tools* показывает три инструмента со
схемами, *Resources* — каталог и записи, *Prompts* — шаблон. Кнопка *Call*
отправляет запрос и показывает JSON-ответ.

## 3. Примеры запросов от лица пользователя

**Пример 1. Запись на мероприятие**

> Пользователь: «Запиши меня на хакатон, я Иванов, группа 4-1.»
>
> Ассистент читает `catalog://events`, находит сессию `s-0001` (свободно 1 место),
> вызывает `create_registration(session_id="s-0001", user_id="u-0001")`.
>
> Ответ инструмента:
> ```json
> {
>   "ok": true,
>   "registration_id": "r-0c5b66fb",
>   "ticket_id": "t-ea7084d3",
>   "qr_payload": "r-0c5b66fb|s-0001|2026-11-08T16:28:05+00:00",
>   "status": "Записан",
>   "free_seats": 0
> }
> ```
>
> Ассистент: «Записал вас на 20 ноября, 18:00, Главный корпус, ауд. 721. Билет
> в приложении, работает без сети. Свободных мест больше нет.»

**Пример 2. Мест нет**

> Пользователь: «Тоже хочу на хакатон.»
>
> Ассистент вызывает `create_registration` и получает:
> ```json
> { "ok": false, "code": "NO_SEATS", "message": "Свободных мест нет",
>   "free_seats": 0, "waitlist_length": 1 }
> ```
>
> Ассистент: «Мест нет, но в очереди уже один человек — могу поставить вас вторым.
> Когда место освободится, придёт приглашение со сроком ответа 30 минут.»

**Пример 3. Отмена и передача места**

> Пользователь: «Отмените мою запись, не смогу прийти.»
>
> `cancel_registration(registration_id="r-0001", reason="Передумал")`:
> ```json
> { "ok": true, "status": "Отменено", "freed_seat": true,
>   "offer_to": { "registration_id": "r-0003", "user_id": "u-0004",
>                 "expires_at": "2026-11-08T16:58:05+00:00" } }
> ```
>
> Ассистент: «Отменил. Место предложено следующему в очереди, у него 30 минут.»

**Пример 4. Отметка на входе**

> Организатор: «Отметь билет, вот код.»
>
> `check_in_ticket(qr_payload="r-0002|s-0001|...")` → `already_marked: false`,
> повторный вызов → `already_marked: true` с тем же временем. Дублей нет.

## 4. Решения и ограничения MVP

**Своя SQLite, а не рабочая PostgreSQL.** Демонстрация не должна оставлять следов
в данных, а mock-база поднимается одной командой без Docker. Схема повторяет
физическую модель по смыслу: `app_user`, `event`, `session`, `registration`,
`ticket`, `seat_offer`.

**Проверки в коде, а не только в БД.** SQLite не умеет частичные индексы с
перечислениями и триггеры такой сложности, поэтому правило «мест не больше
лимита» проверяется в `create_registration` внутри одной транзакции. В рабочей
PostgreSQL то же правило держит триггер `registration_seat_insert` — код MCP для
продакшена переключается на API, а не на базу.

**Идентификаторы упрощены** (`u-0001`, `s-0001`) — в продакшене UUID, как в схеме.

**Что не реализовано и почему.** Очередь уведомлений, модерация и выгрузки в
MCP не вынесены: это действия с длинным побочным эффектом, ассистенту они не нужны,
а каждая лишняя операция расширяет поверхность атаки.
